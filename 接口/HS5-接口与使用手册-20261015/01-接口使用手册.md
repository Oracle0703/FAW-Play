## 2. 如何查一个接口

1. 在 `index.html` 输入功能或名称，例如 `空调`、`ICarATCManager`、`getCarSpeed`、`QisiMusicInfo`。
2. 优先看“接口声明”“回调合约”“SDK管理器”，必要时勾选包含生成辅助类/内部实现。`*SDK` 接口不是一定可直接 `transact` 的 Binder 合约。
3. 查看准确类型、事务号、字段、常量与来源。空白事务号表示本次没有从相应 Stub 静态常量关联到编号，**不能按列表顺序补号**。
4. 先核对目标版本和权限，再对照 Proxy/Stub 确定 Parcel 参数顺序、nullable 标记、返回类型、异常头、同步/oneway。完整目录不声称所有方法的 wire 格式已逐项审核。
5. 在本手册中查已整理的调用条件、取值和生命周期。没有语义证据的接口保留原始值，不凭名称推测物理单位。

JSON/CSV 中的 Java 签名来自 DEX 描述符。泛型参数已被 DEX 类型擦除，通常只能看到 `List/ArrayList`；参数名和注释没有自动恢复。数据字段的排序是元数据顺序，不是 `writeToParcel()` 顺序。

## 3. Qisi 连接与 Binder 调用

### 3.1 绑定根服务

显式组件：

```java
new ComponentName("ltd.qisi.adapterservice", "ltd.qisi.adapterservice.QISIAdapterService")
```

根 Binder descriptor：`ltd.qisi.adapterproxy.IVehicleRemoteClienter`。当前导航代码使用显式组件和 `Intent.ACTION_MAIN`，车辆客户端显式绑定相同组件。`bindService` 返回 true 只说明绑定请求受理，应等待 `onServiceConnected`，并核对实际 descriptor。

根事务 **1** 为 `IBinder queryBinder(int moduleId)`：

```text
request: writeInterfaceToken(rootDescriptor), writeInt(moduleId)
transact(1, request, reply, 0)
reply:   readException(), readStrongBinder()
然后核对模块 Binder 的 getInterfaceDescriptor()
```

常用模块如下。完整 55 组见模块表；编号只在此根服务上下文有效，不是 CAN 帧 ID、Android property ID 或 HIDL transaction。

| ---: | --- | --- |
| 1 | IBluetoothExtraManager | 蓝牙扩展 |
| 5 | ICarAudioManager | 音源/音量/焦点 |
| 8 | ICarInstrumentRelatedManager | 仪表导航、音乐、电话等消息 |
| 13 | ICarSystemControlManager | 系统控制与全屏导航状态 |

### 3.2 正确的基本调用方式

普通同步 getter：`writeInterfaceToken(模块descriptor)` → 按 Proxy 顺序写参数 → `transact(code,...,0)` → 检查布尔返回 → `readException()` → 按类型读值。`float` 必须 `readFloat()`，不能读取为 int 后自行换算。

工作线程执行 Binder I/O；UI 线程只更新显示。可缓存仍存活的模块，服务死亡时清空并重绑。每个 Parcel 都在 `finally` 回收。分别处理 `transact=false`、空模块、descriptor 不匹配、`SecurityException`、`DeadObjectException` 和畸形/截断 reply。Binder 同步调用不能靠普通 Future 取消强行中断，应合并更新并避免无界堆积请求。

回调注册/注销通常写 `StrongBinder`，但每个接口独立核实。本包已审核的 ATC、SCCU、车辆状态回调 Proxy 使用 **FLAG_ONEWAY=1、reply=null**。接收端先 `enforceInterface()`，校验 payload 长度和区域索引，再更新状态；不是为所有其他厂商回调一律声明 oneway。

完整只读 Java 示例：[Hs5ReadOnlyProbe.java](examples/Hs5ReadOnlyProbe.java)。它接受已经绑定的根 Binder，仅提供车速原始值、挡位原始值和环境温度读取；不包含车控下发。

## 5. 空调：模块 33 / ATC

SDK：`CarACManager`；Binder：`ltd.qisi.adapterproxy.ICarATCManager`。原厂 HVAC 实际调用和服务实现均已核对，当前 xcertplay 已接入读取与内部显式控制。

| 功能 | 读事务/参数 → 返回 | 写事务/参数 → 返回 |
| --- | --- | --- |
| 前排开关 | 1 () → int | 2 (int command) → int |
| AUTO | 3 (int **-1**) → int | 4 (int command) → int |
| 分区同步 | 5 (int **-1**) → int | 6 (int command) → int |
| A/C 压缩机状态 | 7 (int **-1**) → int | 8 (int command) → int |
| 出风模式 | 9 (int **0**) → int | 10 (int **0**, int mode) → int |
| 左右温度 | 11 (int side) → **float °C** | 12 (int side, **float °C**) → int |
| 风量 | 13 () → int | 14 (int level) → int |
| 内外循环 | 15 () → int | 16 (int command) → int |
| 前除霜 | 17 () → int | 18 (int command) → int |
| 环境温度 | 93 () → **float °C** | 无 |
| 回调 | 85 注册 / 86 注销 | 写 listener Binder，返回 void |

取值与原厂 UI 语义：

- 左右 `side=0` 主驾、`1` 副驾。设定温度 **15..35°C、0.5°C 步进**；getter 已给出摄氏度。环境温度为 -40..86.5°C，不能再做 raw/2-40。
- 风量 0..7。出风模式 **1=脸、3=脸+脚、5=脚、6=脚+窗、7=窗**；控制不使用其余值。
- 开关、AUTO、同步、A/C、前除霜的**下发**关=1、开=2，不是 Boolean 0/1。
- 原厂 UI 对开关/AUTO/同步/前除霜通常以回读 1 显示开，0/2 显示关；A/C 的回读 1 和 2 都显示开启。不自行解释 A/C 状态 2 的物理子状态。
- 循环下发外=1、内=2；接口实现接受 0..2，但 **0 含义未闭合**，业务操作不要用 0 作为已知内外循环。

上述开关和档位语义来自后续原厂 UI 静态核查，补足了早期源文件注释中的“未知”。见 [ui-semantics 证据](evidence/hs5-comfort-ui-semantics-3222.json)。本车反馈仍需确认。

回调 descriptor：`ltd.qisi.adapterproxy.listener.ICarATCStateListener`：

| 事务 | 内容/参数 |
| ---: | --- |
| 1 / 2 / 3 / 4 | power / auto / sync / compressor，各 int state |
| 5 | blowMode(int side, int mode)；当前快照只取 side=0 |
| 6 | temperature(int side, **float temperature**) |
| 7 / 8 / 9 | fan / circulation / frontDefrost，各 int state |

后排空调、后除霜、净化等即使出现在完整 SDK 中，也不能因此认定本车实现有效；存在默认返回 -2 的方法。

## 6. 座椅与车型能力：模块 49 / 31

前排座椅必须使用原厂 HVAC 实际采用的 **SCCU** 路径，不能仅因 ATC 有同名座椅方法就更换通道。

| SCCU 事务 | 方法 | 参数/返回 |
| ---: | --- | --- |
| 3 | getFrontSeatVentLevel | int side → int feedback |
| 4 | setFrontSeatVentLevel | int side, int command → int result |
| 7 | getFrontSeatHeatLevel | int side → int feedback |
| 8 | setFrontSeatHeatLevel | int side, int command → int result |
| 29 / 30 | 注册/注销座椅回调 | listener Binder → void |

`side=0/1` 对应主驾/副驾。**命令关/低/中/高=1/2/3/4；回读关/低/中/高=0/1/2/3**。因此关闭发送 1，不能将 UI 0 直接写给服务。独立 `get/setFrontSeatHeatState` 和 `get/setFrontSeatVentState` 在该实现返回 -2，不应当作独立开关 API。

回调 descriptor：`ltd.qisi.adapterproxy.listener.IVehicleCarSCCUChangedListener`。事务 2=通风、4=加热；均为 `(int side,int level)`。

能力校验走 EOL 模块 31：

| 事务 | 方法 | 使用方法 |
| ---: | --- | --- |
| 4 | getPDSN() → String | 仅内存判型；不记录/发布实际 PDSN |
| 49 | isSupportFRONT_SHS() → boolean | reply 按 Binder boolean 的 int 编码读取，1 表示支持 |
| 50 | isSupportFRONT_SVS() → boolean | 同上，前排通风能力 |

原厂 `carType()` 将 PDSN 前十位 `7901010DD4`、`7901010DD5` 分为 type1/C255；`7901010DD2` 为 type0/C235，其他为 -1。当前控制仅放行已确认 type1 和相应 EOL 能力。零件号 DD52 前缀相符不能代替服务实际返回的 PDSN/EOL。车型判断和能力检查失败时不下发。

## 7. 当前 xcertplay 的应用层用法

本节 API 是当前项目进程内 Kotlin API，不是车机对外 HTTP 接口、导出广播或官方 Apple Ultra API。源码见 [examples/xcertplay-vehicle](examples/xcertplay-vehicle)。

```kotlin
// 宿主持有唯一 owner；宿主结束时关闭 observeHandle 和 lease。
val owner = Any()
val lease = Hs5VehicleData.acquire(context, owner)
val observeHandle = Hs5VehicleData.observe { snapshot ->
    val temperature = snapshot.value(Hs5VehicleField.AMBIENT_TEMPERATURE)
    // null 显示“未获取”；不要显示成 0°C。
}
// 不再需要时：
observeHandle.close()
lease.close()
```

观察者本身不保活连接。owner 按对象身份计数，同一个 owner 重复 acquire 不会新增一份所有权；保留首次返回的 lease 并明确释放。最后一个 owner 释放后注销回调、解绑并清空快照。观察通知回到主线程；底层 Binder 读取在工作线程。

快照连接状态有 STOPPED、UNSUPPORTED_DEVICE、CONNECTING、CONNECTED、UNAVAILABLE、PERMISSION_DENIED。`snapshot.value(field)` 只在连接有效、数值有限且样本年龄不超过 **5 秒**时返回值。轮询间隔 1 秒、车型/EOL 复核间隔 10 秒；这不是服务实时性能保证。重连按代次隔离旧回调和旧读取。

当前 32 字段：空调 10 项、环境温度 1 项、前排座椅 4 项、速度/挡位/燃油/低油量/续航/里程/油耗 7 项、四门 4 项、尾门 1 项、位置灯 1 项、四轮胎压 4 项。精确 enum 见 `Hs5VehicleState.kt`。

显式内部控制示例（仅在用户操作后调用，**示例不会自动执行**）：

```kotlin
Hs5VehicleData.execute(Hs5VehicleCommand.ClimateTemperature(0, 22.5f)) { result ->
    when (result) {
        is Hs5VehicleCommandResult.SentToService -> {
            // 仅原厂应答。等待新的快照反馈，不乐观修改温度。
        }
        is Hs5VehicleCommandResult.Rejected -> { /* 显示 reason */ }
    }
}
// 座椅加热关闭：SeatLevel(side=0, heating=true, encodedLevel=1)
```

所有控制校验参数、有效连接、DD4/DD5 判型、相应 EOL、目标字段新鲜度。拒绝原因包含 `invalid-parameter`、`vehicle-disconnected`、`vehicle-model-unverified`、`feature-unavailable`、`state-unavailable`。服务异常和具体返回需按客户端 result 记录；不能把 SentToService 当作物理执行成功。

当前管理页是只读状态卡，没有新增空调/座椅按钮，没有导出车控网络/广播入口，Ultra 开关仍禁用。内部车控存在不等于官方 Ultra 交付完成。

结束导航时分别清0。HUD 转向使用当前厂商映射文件；不要把 CarPlay、地图 NEW_ICON、仪表和 HUD 编码视为同一枚举。部分 lane/hazard 方法在本包底层默认返回 -2，类中有方法不等于 HUD 可显示车道/危险提示。HUD 的电话、音乐通路尚未完整闭合。

### 8.3 地图画面与原厂退出

画面通过 Android Display/Presentation 与独立视频面处理。当前代码筛选 `Cluster-Display`、1920×720，使用不获取输入焦点的窗口并要求 overlay 权限；这些筛选条件不是当前车机实际存在副屏的证明。pixel stream 协商、surface、FullMap 状态、文字导航、HUD 是不同验收项。

系统控制模块13的回调注册/注销为64/65。listener `IVehicleSystemControlListener` 事务15携带 String，请求为 `HardKeyQuit` 时当前 App 隐藏地图。地图隐藏、副屏流关闭和整个 CarPlay 会话结束应分开处理，避免关闭仪表地图误结束中控会话。

当前 DiPlay 三指水平手势控制仪表显示，实际行为还受授权、导航状态和显示准备状态约束；不要用软件手势替代原厂安全提示仲裁。

### 8.4 主题与常量边界

主题模块53只有 `getClusterThemeVersionCode`、`changeClusterTheme`、`updateClusterTheme`、`getSystemThemeToInt`。它不是实时仪表导航入口，也不是 CarPlay Ultra 实现。

41 组 CarPlay 常量是静态整数类型，不是可用 `ordinal()` 编号的 Java enum。关键例子：左1/右2/直3/掉头4/进环岛6/出环岛7；距离单位 KM0/MILES1/M2/YARDS3/**FT4（英尺）**；CarPlay 导航开始0/结束1。常量只能用于其所属类型，不能套用本节原生导航状态1/0。

`CLUSTER_SOURCE_*` 实际为外层 Constants 中11个整数，嵌套 SOURCE/SOURCE_STATUS 是注解类型。`OPEN_LYRIC/CLOSE_LYRIC` 来源于 QisiSpeech 语音语义，尚未找到可交付的仪表歌词文本/时间轴协议。

## 9. 方向盘、视图焦点与日夜

根服务组件：`ltd.qisi.systemservice/ltd.qisi.systemservice.QisiSystemService`；descriptor：`ltd.qisi.systemmanager.ISystemServiceInterface`。它是另一条服务，不通过 Qisi Adapter 的 queryBinder。

| 事务 | 签名与编码 |
| ---: | --- |
| 12 | registerHardKeyListener(String package, String id, **int[] keys, boolean permanent**, IHardKeyListener) |
| 13 | unregisterHardKeyListener(String package, String id, **boolean permanent, int[] keys**, IHardKeyListener) |
| 5 | requestViewFocusWithListener(int view, IViewFocusChangedListener) → int |
| 6 | abandonViewFocusWithListener(IViewFocusChangedListener) → int |
| 10 | queryViewFocus(int view) → int |

注册和注销参数顺序不同。boolean 在此 Parcel 以 int 表示。当前订阅88/87切歌、5电话、259和110 MODE，`permanent=false` 走临时独占栈，结束/离开时释放。硬按键回调 descriptor 为 `IHardKeyListener`，事务1参数为 `(int key,int action)`；action0短按、1长按、2长按完成、3电话丢弃，不是 Android DOWN/UP。

视图焦点使用原厂 Carlink view38，保留倒车/E-CALL 等原厂优先级。request 被接受不代表之后一直拥有焦点；按回调和查询状态恢复/释放。完整防阻塞/代次处理见 `examples/diplay-system/HongqiWheelControls.java`。旋钮虽有 D-pad/HID 映射代码，仍需实体旋钮事件到达入口的实测。

日夜源读取模块15事务19位置灯。当前 DiPlay 500ms 采样，0浅/1深，其他unknown，失败重试。位置灯、Android uiMode、App主题与原厂仪表主题是不同状态；分别验收。历史开灯变化记录不能覆盖当前所有主题和固件。

## 10. 音频、麦克风与蓝牙媒体交接

优先使用当前工程的音频路由/焦点协调层。原厂有 `android.car.media.CarAudioAttribute.createPlayAudioAttributes(int)`，把厂商 usage 转换为合法 Android usage，并携带 `usage` Bundle 与 bus 地址标签：

| 厂商 usage | 值 | 标准 usage | 目标地址 |
| --- | ---: | ---: | --- |
| CarPlay电话 | 18 | 2 VOICE_COMMUNICATION | BUS03_CALL |
| CarPlay导航 | 19 | 12 ASSISTANCE_NAVIGATION_GUIDANCE | BUS01_NAVIGATION |
| CarPlay Siri | 20 | 1 MEDIA | BUS09_CARPLAY_SIRI |
| CarPlay铃声 | 25 | 1 MEDIA | BUS10_CARPLAY_RINGTONE |

**不能把18/19/20/25直接传给普通 AudioAttributes.Builder.setUsage。** 原厂类为隐藏/厂商运行时 API，不在通用 SDK 中；使用前核实类、签名和异常，按项目现有回退处理，工厂方法产生属性也不代表焦点和物理路由已经获准。

Qisi 音频模块5完整方法见目录，涵盖 request/abandonAudioFocus、group volume、mute、navigation mix 和 listener。它与标准 AudioManager 焦点、AudioTrack 属性和 OEM CarAudioManager 是不同层；不要把来源编号、usage、bus 和 stream 编号混用。

当前 DiPlay 的 `HongqiNavigationMixing` 通过 `android.car.Car` 的 audio manager 调用 `turnDownMediaVolumeWhenDuckedByNavi(boolean)`，关联 `mixing_down_media_volume`、所有者与恢复记录。这个全局原厂混音策略与 App 内 VolumeShaper 0.75（约-2.5dB）是不同机制；应用结束恢复只处理自己持有的临时策略，并尊重外部改动。

录音常量 `AlfusAudio`：PHONE_8K4、PHONE_16K5、FACETIME6、SIRI7 是 OEM 模式，不是 `MediaRecorder.AudioSource`。该类本身没有已确认公共设置方法；FM1388 的 getMode/setMode 合约也不自动证明这几个编号可以直接套用。原厂平台是 Intel/Alfus/IAS/FM1388 证据，不按高通 DSP 实现解释。

无线 CarPlay 媒体与蓝牙 A2DP 同时播放会冲突。当前项目有 HFP 保留、A2DP 交接及恢复逻辑，不能为了音乐而关闭整条蓝牙。MediaSession 中显示歌曲不等于原厂仪表已经收到歌曲。Siri/电话须检查录音授权、焦点、真实输入输出设备、采样、AEC及中断恢复；只听到音乐不能验收这些场景。

## 11. 无线、USB 与认证配置

3092 对照材料证实 `p2p0`（专用 Wi-Fi Direct）和 `wlan0`（普通 Wi-Fi）分开。wlan overlay 中 `p2p_disabled=1` 不能推出专用 p2p0 禁用。

当前 HS5 无线流程：点击连接 → 确认录音等必需授权 → 请求蓝牙可发现并等待状态 → 系统/iPhone 完成首次配对信任 → App 创建 P2P GO → 读取真实组信息 → iAP2 交给 iPhone → iPhone 加入 → AirPlay/CarPlay。iPhone 作为普通 Wi-Fi 客户端加入 GO，不要求使用 Android P2P 同伴发现界面。

- Android9 `WifiP2pManager.createGroup(channel,listener)` 不接受自定义 SSID/密码/频率。读 `requestGroupInfo` / `requestConnectionInfo` 的实际结果；建组请求受理不等于 iPhone 入网。
- 3092 对这三个 GO 操作只检查已声明 Wi-Fi 权限，未走扫描/定位门槛；`requestPeers` 是另一条扫描路径，不能外推。可选 GPS reporting 仍单独需要定位授权。
- 3092 `BluetoothAdapter.setScanMode(int,int)` 为 public/light-greylist；当前请求120秒可发现，等待真实模式广播最多2秒，失败回退系统可发现确认页。返回 accepted 不等于射频模式已变。
- API28 蓝牙使用安装时 BLUETOOTH/BLUETOOTH_ADMIN；Android12/13测试手机的 CONNECT/SCAN/ADVERTISE/NEARBY_WIFI_DEVICES 要独立判断。
- 无线直连不需要 VPN/TUN。USB NCM 是另一条有线路径，VPN consent 不能套到无线说明。
- 退出只移除 App 能证明自己持有的临时组，不清空用户或其他应用的网络组。

`AppleFunction.conf` 指向 `/dev/i2c-0`、地址0x10/0x11，并带 EXEED/Neusoft 等复用配置。这些**不能证明主板已装 MFi 芯片**。已核系统有 AppleServiceNative init/SELinux 残留，但未找到相应可执行文件；`apple-server` 的实际 Binder 协议未确认，不提供猜测事务号。访问 I2C 需 Linux节点权限、SELinux和真实服务共同允许；Manifest不能代替它们。`carplay_data_file` 是 SELinux 标签，不是独立分区。

当前使用项目既定认证后端；本手册不包含证书私钥、配对身份、OOB key 或 MFi 秘密材料，也未实现 Apple 官方 Ultra 协议。

## 14. 调用后的验收与错误定位

正确次序为：版本/descriptor → 访问权限 → 模块与业务支持 → 参数编码 → 服务应答 → 新鲜反馈 → 原厂实际效果 → 中断与恢复。分别记录，不能把所有失败归为权限。

| 现象 | 首先检查 |
| --- | --- |
| 绑定返回false/空Binding | 组件存在、启用、导出、Intent和绑定权限 |
| queryBinder空/null或transact=false | 模块编号/固件差异、服务状态、实际descriptor |
| SecurityException / SELinux denial | 实际UID/签名、权限/AppOps、服务端检查、Binder/HAL策略 |
| 返回-2/负错误/特殊无效码 | 功能未实现、车型/EOL、未更新；不作为0显示 |
| 数字合理但物理量错误 | float/int读取、参数顺序、重复缩放、单位/枚举混用 |
| 有服务应答、界面不变 | 等待新反馈、原厂互斥/覆盖/条件、实际车端执行；不改成“已成功” |
| 重连后旧状态复活 | Binder死亡清理、连接代次、样本时间戳和订阅所有权 |
| 地图关闭导致中控断流 | 副屏/地图所有权与整个会话生命周期混淆 |

逐项验收表和只读工具见 [03-权限与实车验收](03-权限与实车验收.md)。
